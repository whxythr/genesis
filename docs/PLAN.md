## 1. Ключевые архитектурные решения (предлагаю)

1. **Деньги**: `int` minor units везде; таблица разрядности `{JPY:0, KZT:2, USD:2, EUR:2, GBP:2, KWD:3}`. FX — `Decimal` из строки, округление `ROUND_HALF_UP` в minor units базовой валюты. Одна функция `convert(amount_minor, src, dst, rate) -> int` — используется и генератором, и валидатором, и reconcile-политикой.
2. **Главная книга в базовой валюте.** Все проводки `ledger.csv` в `base_currency`; валюта документа видна в документе. Тогда `fx_error` = «сумма в книге ≠ сумма документа × курс по правилу policy» — однозначно проверяемо. Счёт и его платежи в одной валюте; курсовая разница при оплате проводится на `FX_GAIN_LOSS` (это корректный «подозрительный» случай).
3. **План счетов**: `AR`, `REVENUE`, `CASH`, `UNAPPLIED_CASH`, `FX_GAIN_LOSS`, `REFUNDS`. Каждая бизнес-операция = транзакция из ≥2 строк с общим `txn_id`.
4. **Добавляю колонки сверх CLAUDE.md** (иначе инварианты/доказательства неадресуемы): `ledger.csv: txn_id`, `fx.csv: fx_id`. См. вопрос Q1.
5. **Изоляция**: открытые файлы `episodes/<split>/<episode_id>/`, закрытые `grader_data/<split>/<episode_id>/`. `store.py` получает только путь к открытой директории и грузит всё в память при `reset` (агент вообще не трогает ФС). Оценщик — отдельный процесс (`subprocess`, JSON по stdin/stdout); среда передаёт ему `episode_id` + findings, получает reward.
6. **ID**: непрозрачные, из `rng` эпизода (`INV-7KQ2M9XA`, `PAY-…`, `R-…`, `T-…`, `FX-…`, `D-…`), без «dup/err», без порядка. Префикс говорит только о таблице. Порядок строк в файлах — сортировка по ID (т.е. псевдослучайный, ошибки не в конце).
7. **Курсоры**: `base64url(json({"t":table,"o":offset,"e":episode_hash}))` с HMAC от episode-соли — стабильны, непрозрачны, курсор от другого эпизода → ошибка `BAD_CURSOR`.
8. **Калькулятор**: свой токенизатор + рекурсивный спуск по `Decimal`; `+ - * / ( )`, унарный минус; длина ≤200 символов, глубина ≤20, |результат| ≤ 1e18; деление на 0 → `CALC_ERROR`.
9. **Коды ошибок** (фиксированные): `UNKNOWN_ACTION, BAD_ARGS, UNKNOWN_TABLE, NOT_FOUND, BAD_CURSOR, CALC_ERROR, EPISODE_DONE`. Каждый расходует шаг.

## 2. Определения ошибок (черновик → в DESIGN.md «Решения»)

Валюта `expected_amount_minor` — **всегда `base_currency`** (как отражено в книге). Допуск: `|claimed − expected| ≤ max(1, floor(0.001·expected))`.

| type | канонический `affected_ids` | expected | минимально достаточный evidence set |
| --- | --- | --- | --- |
| `duplicate_invoice` | `[invoice_id дубля]` (дубль = тот, у которого `issued_at` позже; при равенстве — больший doc_id) | сумма дубля в книге | `{doc_id оригинала, doc_id дубля, txn_id проводки дубля}` |
| `unapplied_payment` | `[payment_id]` | нераспределённый остаток (в base) | `{doc_id платежа, doc_id счёта, txn_id распределения}`; если `invoice_refs = null` — `{doc_id платежа, txn_id поступления}` |
| `fx_error` | `[invoice_id или payment_id]` документа с неверной конвертацией | `|книга − правильная конвертация|` в base | `{doc_id документа, fx_id правильного курса, txn_id проводки}` |
| `period_cutoff` | `[invoice_id или payment_id]` | сумма операции в base | `{doc_id документа, txn_id проводки}` + константа `POLICY` |

Правило курса (policy): курс на **календарную дату операции в timezone компании**; `fx.csv` содержит курс на каждый день периода ±7 дней, т.е. «ближайшая предыдущая дата» не нужна (нет неоднозначности).

**Сценарий A** (частичный платёж в иностранной валюте на границе периода): платёж EUR датирован 1-го числа следующего периода по времени компании (в UTC — ещё последний день), проведён в текущем периоде, конвертирован по курсу не той даты и распределён частично → три issues: `period_cutoff` (сумма проводки), `fx_error` (разница курсов), `unapplied_payment` (остаток). Порядок вычисления сумм и почему они не «съедают» друг друга — распишу в DESIGN.md с числовым примером.
**Сценарий B** (дубль, частично оплаченный): платёж ссылается на дубль и покрывает его частично → `duplicate_invoice` (полная сумма дубля) + `unapplied_payment`? — см. Q4.
