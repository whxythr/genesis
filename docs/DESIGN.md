# DESIGN — RL-среда «ИИ-аудитор»

Статус: фазы 1–3 закрыты (контракт, 4 типа ошибок, 2 сценария взаимодействия, валидатор доказательств, изоляция, детерминизм, инвариантность, 4 базовые политики).

## 1. Устройство

```
seed + config ──► generator (в процессе оценщика)
                    company.py   документы: счета, платежи, возвраты, фон, FX
                    posting.py   книга выводится из документов (двойная запись)
                    invariants   независимый детектор по ОТКРЫТЫМ данным
                    errors.py    инъекция = изменение документа / правила проводки
                 ├─► open bundle ──► AuditEnv (store, tools) ──► агент
                 └─► truth / provenance (остаются в процессе оценщика)
агент ── submit ──► AuditEnv ──► grader process (JSON по stdin/stdout) ──► reward
```

- **Оценщик — отдельный процесс** (`grader/service.py`). Он генерирует или читает эпизод,
  держит truth и отдаёт среде только открытый bundle. Ни одна команда протокола
  не возвращает truth, provenance или seed.
- **Среда не трогает ФС**: `Store` строится из bundle в памяти; агент не может указать путь.
- **Книга выводится из документов** (`post_ledger`). Ошибка = минимальная причина (изменённый
  документ или override правила проводки); все изменения строк книги — её следствие и
  записаны в `provenance.ledger_diff`.
- **Независимый валидатор** (`generator/invariants.py`) заново выводит ожидаемые проводки из
  документов, `fx.csv` и policy, не используя код проводок. На чистой истории — 0 нарушений;
  после инъекции обнаруженные аномалии должны **ровно** совпасть с truth (тип, ID, сумма,
  доказательства), иначе генерация падает (`GenerationError`).

## 2. Решения

| # | Решение | Причина |
| --- | --- | --- |
| D1 | Книга целиком в базовой валюте; документы в своей валюте | `fx_error` проверяется однозначно: книга vs документ × курс policy |
| D2 | Добавлены колонки `ledger.txn_id`, `fx.fx_id`; поле `payments.kind` (`receipt`/`refund`), `payments.entity_id`, `invoices.entity_name` | без `txn_id` нельзя проверить баланс транзакции, без `fx_id` — сослаться на курс; `kind` нужен для возвратов |
| D3 | `invoice_refs` = список `{invoice_id, amount_minor}` в валюте платежа или `null` | частичное и множественное распределение должно быть видно в документе |
| D4 | Курс: строка `fx.csv` с датой = календарная дата операции **в часовом поясе компании**; `fx.csv` покрывает период ±7 дней | нет неоднозначности «ближайшей предыдущей даты» |
| D5 | Конвертация: `Decimal`, `ROUND_HALF_UP` до minor unit цели; курс = единиц цели за 1 единицу источника | опубликовано в `policy.json` |
| D6 | Погашение AR в валюте: `relief = convert(cum_after) − convert(cum_before)` по курсу проводки счёта, разница → `FX_GAIN_LOSS` | сумма частичных погашений точно закрывает AR без «копеечных» хвостов |
| D7 | Период `[start, end)`, сравнение по моментам времени; документы платежей несут смещение банка (часто `+00:00`) | реалистичные ловушки часовых поясов |
| D8 | Дубль: тот же `entity_id`, валюта, `total_minor` и **идентичные** `line_items`; дублем считается более поздний | подписки с той же суммой отличаются текстом периода — это корректный отвлекающий случай |
| D9 | Валюта `expected_amount_minor` — **всегда базовая** | единое правило для всех типов |
| D10 | «Независимые суммы»: сумма каждой ошибки считается по корректному курсу policy, как будто остальные ошибки уже исправлены | согласованность во взаимодействующих сценариях (фаза 3) |
| D11 | Допуск суммы τ = **0** для всех четырёх типов (`matcher.TOLERANCE_MINOR`), сравнение целых minor units точное | все эталонные суммы получаются целочисленной арифметикой с опубликованным `ROUND_HALF_UP`, поэтому агент, следующий policy, получает их точно; совпадает с умолчанием определений проверок (20.11). Ранее было `max(1, expected//1000)` — заменено (см. D44) |
| D12 | Канонические `affected_ids`: duplicate → `[invoice_id дубля]`; unapplied → `[payment_id]`; fx → `[invoice_id или payment_id]`; cutoff → `[invoice_id или payment_id]` | один ID на вывод, стабильный при переименовании |
| D13 | Минимальные наборы доказательств: duplicate `{doc оригинала, doc дубля, txn дубля}`; unapplied `{doc платежа, txn платежа}`; fx `{doc, fx_id правильного курса, txn}`; cutoff `{doc, txn}` | достаточность проверяется валидатором; лишние ID не мешают |
| D14 | Алиасы доказательств: `invoice_id`/`payment_id` ≡ свой `doc_id`; `row_id` ≡ свой `txn_id`. Разрешение по пространствам имён: если одна строка — ID в двух таблицах, она разрешается в обе цели | агенту не нужно угадывать «правильную» форму ID; результат не зависит от того, как жюри переименовало ID в разных пространствах |
| D15 | Любой несуществующий `evidence_id` → вывод не может быть TP (но **не** −1 для всего ответа) | −1 только за нарушение схемы/лимитов (Q7 в PLAN) |
| D16 | Неизвестный `type` — не ошибка структуры, а FP | нормализация типов публикуется |
| D17 | `inspection_steps` = шаги до submit, включая ошибочные, без самого submit; при усечении = число сделанных шагов (100) | Q5 |
| D18 | Усечение (100 шагов или 60 с) → оценка с пустыми findings. На чистых книгах это F1=1 → награда 0.8 | строго по ТЗ; разница с честным submit — штраф за шаги |
| D19 | Матчинг: максимальное паросочетание (Кун). Tie-break ровно по определениям: `issue_id` по кодовым точкам Unicode, затем лексикографически наименьшая отсортированная последовательность пар `(issue_id, индекс вывода)` | размер максимального паросочетания единственен → tie-break не влияет на TP/FP/FN и награду, только на то, какой из одинаковых выводов считается сопоставленным (тесты M10, M11) |
| D20 | P и R при нулевом знаменателе = 0 (в т.ч. на чистых книгах с пустым ответом), F1 = 1 в этом случае | ТЗ; поэтому средние P/R в таблице ниже 1 даже у oracle |
| D21 | `list_records` имеет опциональный `filter` (точное совпадение по белому списку полей) | новых действий нет; экономит шаги, не раскрывает эталон |
| D22 | Счета в `list_records` — сводка без `line_items`; полный документ — `get_document` | у `get_document` есть смысл; дубль требует сравнить позиции |
| D23 | Курсоры: base64(JSON{table, filter-digest, offset}) + HMAC; привязаны к эпизоду, таблице и фильтру | стабильны при повторе, подделка → `BAD_CURSOR` |
| D24 | Ошибки инструментов: фиксированный код + фиксированное сообщение, ввод не отражается | нет утечек и prompt-reflection |
| D25 | Режим eval: reward=0 и `info={}` на каждом шаге; результаты доступны только после `finalize`, после которого сессия не открывает новых эпизодов | агент не может учиться на скрытых эпизодах внутри прогона |
| D26 | Reset посреди эпизода оценивается как `abandoned` (= усечение, пустой ответ) | нельзя «перезапустить» плохой эпизод бесплатно |
| D27 | ID: префикс таблицы + 8 символов из алфавита без 0/1/I/O; ID строк книги детерминированно выводятся из соли эпизода | ID стабильны при перепроводке, без смысловых подсказок |
| D28 | CSV: пустое поле = `null`; JSONL с отсортированными ключами; LF (`.gitattributes`) | байт-в-байт воспроизводимость |
| D29 | Валидация JSON Schema — собственный мини-валидатор (подмножество ключевых слов) | ноль runtime-зависимостей |
| D30 | Oracle получает truth от runner'а (harness), а не от среды | в среде нет «чёрного хода» к эталону |
| D31 | `fx_error` = документ в иностранной валюте проведён по курсу **другой даты** из `fx.csv` (варианты: предыдущий/следующий день, курс недельной давности, UTC-дата вместо даты в поясе компании). Цели: неоплаченные счета или полностью распределённые поступления | неверный курс остаётся «правдоподобным» (он есть в таблице); у оплаченных счетов ошибка размазалась бы по погашению |
| D32 | При fx-ошибке в поступлении AR гасится по курсу счёта, а разница уходит в `FX_GAIN_LOSS` → единственный симптом — строка `CASH` ≠ сумма × курс policy | ровно одно расхождение |
| D33 | `period_cutoff` = документ датирован **после** конца периода (60 с … 30 ч), а проводка поставлена в последние 6 ч периода. В 60 % случаев, где смещение документа меньше смещения компании, дата в тексте документа всё ещё читается как последний день периода («ловушка часового пояса») | проверяется сравнение моментов, а не строк |
| D34 | Цели cutoff: счета без платежей и поступления, которые являются последним расчётом по своим счетам (без возвратов) | порядок кумулятивного погашения не меняется → нет побочных расхождений |
| D35 | Сумма cutoff = документ × курс policy на **его** (внепериодную) дату; `fx.csv` покрывает ±7 дней | правило «независимых сумм» (D10) |
| D36 | Достаточность доказательств проверяется при генерации: каждая issue заново выводится **только** из записей своего набора (`generator/evidence.py`); удаление любого ID из минимального набора делает вывод невозможным (тест) | требование «из доказательств однозначно выводятся тип, ID и сумма» |
| D37 | Деньги, распределённые на счёт-дубль, считаются **нераспределёнными** (опубликовано в `policy.documents.unapplied_rule` и в тексте задачи) | дубль подлежит аннулированию, деньги нужно перенести на оригинал; без правила сценарий B неразрешим |
| D38 | Сценарий включается, только если включены **все** его типы ошибок | «каждый тип включается/выключается отдельно» должно соблюдаться и для сочетаний |
| D39 | План эпизода (чистый/с ошибками, сценарии, число ошибок по типам) решается до генерации отдельным RNG и пишется в `provenance.generation.plan` | смена одного решения не сдвигает случайность компании |
| D40 | Пути к `grader_data` передаются процессу оценщика одним сообщением `init` и не хранятся в объекте среды; командная строка процесса их не содержит; повторный `init` запрещён | «среда не имеет ссылки на truth ни в памяти, ни в путях» (тест обходит память среды) |
| D41 | `transform(episode, seed)`: перемешивает строки всех таблиц и биективно переименовывает все ID (RNG от `seed` + исходного `episode_id`); маппинг хранится только на стороне оценщика | парные проверки порядка и ID |
| D42 | Режим eval в `check`: dev прогоняется закрытым — каждая политика в своей сессии, награды приходят из оценщика только после `finalize` | проверяем именно закрытый путь, которым пойдёт жюри |
| D43 | Минимальные суммы: части разбитого платежа ≥ max(100, total/20) minor, возвраты только для счетов ≥ 2000 minor, сценарии для счетов ≥ 1000 minor | иначе крошечная сумма в JPY/KWD округляется до 0 в базовой валюте и даёт строку книги с нулём (найдено валидатором на seed 95) |
| D44 | Нормализация findings по опубликованным соглашениям: `type`, ID и `currency` — **точные строки** (без смены регистра, обрезки пробелов, синонимов); `affected_ids`/`evidence_ids` — множества; повторные выводы не сливаются | определения проверок 20.11, п. 1–5 и M06. Прежняя нормализация (`strip().upper()`) принимала `" kzt"` за `KZT` — это провалило бы M06 |
| D45 | Структура проверяется **до** нормализации и содержит только опубликованные лимиты (30 выводов, 10 `evidence_ids` до удаления повторов, 1000 кодовых точек `explanation`) плюс JSON-типы и обязательные поля. Отрицательная сумма, пустой `affected_ids`, неизвестный тип — FP, а не −1 | п. 7–8 соглашений: «неудачное сопоставление ≠ невалидная структура» |
| D46 | Метрики и награда не округляются | округление до 6 знаков давало 0.313333 вместо 47/150 (ошибка 3.3·10⁻⁷) и −0.829524 вместо −871/1050 (4.8·10⁻⁷) при допуске жюри 10⁻⁹ — тесты 5, 12, 13 Блока 3 провалились бы |
| D47 | Ответ на submit: `{"accepted": true}` или ошибка `INVALID_FINDINGS` (проверка структуры, эталон не нужен); эпизод завершается в обоих случаях | контракт адаптера: «submit возвращает только accepted либо ограниченную ошибку структуры» |
| D48 | Если запрошенную ошибку нельзя разместить в конкретной компании (например, нет иностранного поступления для `fx_error`), компания детерминированно пересобирается с солью `retry<k>` (k ≤ 24; попытка 0 — исходные соли). Номер попытки — `provenance.generation.company_attempt`. Если 25 попыток не помогли — `GenerationError`, а не молча меньше ошибок | раньше генератор молча выдавал меньше ошибок, чем в конфиге (см. разбор сбоев, §7) — жюри, запросившее сценарий D18, получило бы чистую книгу |
| D49 | Необязательный фильтр вариантов в конфиге: `errors.unapplied_payment.variants` ⊆ {`null`, `partial`, `drop`}, `errors.fx_error.variants` ⊆ {`utc_date_instead_of_company_date`, `previous_day`, `next_day`, `week_old_rate`}. Ключ не входит в `default.json`, поэтому `config_id` существующих наборов не изменился | D09–D11 требуют гарантированно и пропуск, и частичное распределение; случайный выбор варианта этого не обеспечивал |
| D50 | Режим `closed` у адаптера = наш `eval`; эпизод из `episode_dir` читает **только процесс оценщика** (открытые файлы + `truth.json`/`provenance.json`), среде передаётся открытый пакет; путь в объекте среды не хранится | «простое сокрытие полей в Python-объекте не считается изоляцией» |

## 3. Генератор

Порядок: план → компания (документы) → подготовка сценариев (легальная часть чистой истории) →
проводки → **инварианты чистой истории** → инъекция → перепроводка → **валидатор совпадает с truth**
→ **достаточность доказательств** → размеры. Любое расхождение = `GenerationError` (детерминированно),
на 300 seed — 0 отказов.

Отвлекающие случаи в каждой компании (по конфигу): подписки (одинаковые суммы раз в неделю, отличается
текст периода), разбитые платежи (часть может не прийти до конца периода — счёт законно открыт),
один платёж на несколько счетов, возвраты, платежи в последние часы периода в смещении, где
календарная дата уже «следующий месяц», платежи и счета в иностранной валюте с курсовой разницей.

Размеры: 200–2000 строк книги, 20–200 документов, 0–12 ошибок. Чистые эпизоды — с вероятностью
`clean_probability` = 0.25; каждый сценарий — с вероятностью 0.3. Состав наборов (seed подряд, без
подбора): train — 4 чистых, 5 со сценариями, 1 с обычными ошибками; dev — 3 чистых, 4 со сценариями,
3 с обычными ошибками.

## 4. Сценарии взаимодействующих ошибок

Общее правило сумм (D10): каждая сумма считается по курсу policy на дату **самого документа**, как будто
остальные ошибки уже исправлены. Поэтому суммы не «съедают» друг друга и каждая проверяется отдельно.

### A. `partial_fx_payment_at_cutoff` — частичный платёж в валюте на границе периода

Что произошло: поступление в иностранной валюте **после** конца периода (часто дата в смещении банка ещё
читается как последний день) проведено в последний день периода, сконвертировано по курсу **дня проводки**,
и на счёт распределена только часть суммы (или ничего). Ожидаются **три** issue на одном `payment_id`:

| issue | сумма | почему |
| --- | --- | --- |
| `period_cutoff` | convert(P, курс даты документа) | операция целиком принадлежит следующему периоду |
| `fx_error` | \|convert(P, курс дня проводки) − convert(P, курс даты документа)\| | ровно ошибка конвертации |
| `unapplied_payment` | convert(P − applied, курс даты документа) | нераспределённый остаток по правильному курсу |

Пример (train `EP-88AR4KC9PB`, база USD, пояс компании +03:00, период декабрь 2026):
платёж `PAY-ARDBS3ZQ` на 182.72 EUR, `2027-01-01T08:34:02+05:30` (= 06:04 +03:00, уже январь),
проведён `2026-12-31T20:57:01+03:00` по курсу 31.12 → CASH 205.15 USD. Курс policy (01.01) = 1.12864 →
правильно 206.23 USD. Распределено 109.63 EUR из 182.72.
→ `period_cutoff` 20623, `fx_error` 20623 − 20515 = 108, `unapplied_payment` = (18272 − 10963) × 1.12864 =
8249 (а строка UNAPPLIED_CASH в книге — 8206, по неверному курсу, **копировать её нельзя**; поэтому в
наборе доказательств есть строка `fx.csv`).

### B. `partially_paid_duplicate` — дубль, который частично оплачен

Что произошло: у счёта в чистой истории есть легальный частичный платёж. Счёт дублируется, и платёж
распределяется на **дубль** вместо оригинала. Ожидаются **две** issue:

| issue | сумма | почему |
| --- | --- | --- |
| `duplicate_invoice` (ID дубля) | convert(total, курс даты дубля) | дубль целиком лишний |
| `unapplied_payment` (ID платежа) | convert(сумма, распределённая на дубль, курс даты платежа) | по D37 эти деньги не распределены на действующий счёт |

Пример (train `EP-2TE6AWJNZF`, база KZT, +09:00): дубль `INV-LB6SQ9ZK` (2352 JPY, подписка за неделю
04–10.08, тот же текст, что у оригинала) → 739196; платёж `PAY-Y6N6F2RW` 1575 JPY распределён на дубль,
курс 15.08 = 3.21641 → `unapplied_payment` 506585. Доказательство требует **обоих** счетов (иначе не
доказать, какой из них дубль), документа платежа, его проводки и курса.

## 5. Изоляция, детерминизм, инвариантность (фаза 3)

- `tests/test_isolation.py`: обход памяти объекта среды не находит маркеров эталона и путей к
  `grader_data`; открытые каталоги содержат только 6 открытых файлов без маркеров; наблюдения и

  идентичны; протокол оценщика не отдаёт truth ни на одну команду, не даёт повторно оценить эпизод и
  перенастроить пути.

  в отдельных процессах; повтор записанных действий даёт идентичные наблюдения и награды.
- `tests/test_invariance.py` и стадия `check`: 20 эпизодов × 3 политики (oracle, reconcile, flag_all) на

## 6. Ограничения (честно)

- Генератор публичный: знание seed позволяет восстановить эталон. Seed агенту не передаётся;
  для скрытых наборов seed нужно брать из большого пространства (≥2^63).
- Тайм-аут 60 с — по wall-clock; это единственный недетерминированный элемент, в тестах
  детерминизма он не срабатывает. Тайминги ответа оценщика в eval не выравниваются искусственно
  (оценка занимает миллисекунды и не зависит от правильности заметным образом, но это не доказано).
- Изоляция процесса оценщика защищает truth, но политика в том же Python-процессе, что и среда,
  технически может обратиться к объекту клиента и вызвать `finalize` в eval; запуск жюри должен
  держать политику отдельно от харнесса (это вне контракта среды).
- Все ошибки детектируются правилами, опубликованными в `policy.json` — это и есть задача сверки;
  reconcile, реализующий все правила, решает эталонные наборы полностью и теряет только штраф за
  шаги. Сложность для обучаемой модели — бюджет шагов, часовые пояса, отличение отвлекающих
  случаев и правильные суммы во взаимодействующих сценариях (см. разбор ниже).
- `fx_error` моделирует неверную **дату** курса (4 варианта, D31); неверное значение курса, которого
  нет в `fx.csv`, или перепутанное направление пары не генерируются. Проверяемо:
  `configs/judge_matrix.json` D12/D13 и `provenance.changes[].variant`.
- Если после переименования одна и та же строка окажется ID в двух таблицах, доказательство
  засчитывается за обе цели (D14) — мягче, чем требовалось бы при типизированных ID. Формат
  `evidence_ids` нетипизирован, иначе это неразрешимо; `test_paired_check` гоняет переименование
  с раздельными префиксами пространств.
- Пересборка компании (D48) делает эпизод с редким сочетанием «дороже» (до 25 попыток, на
  дефолтном конфиге в среднем 1.07 попытки, ≈ 0.1 с на попытку).
- `random_explorer` не инвариантен к порядку строк по построению (выбирает случайно из увиденного);
  инвариантность проверяется на детерминированных политиках.

## 7. Базовые политики и разбор сбоев (измерено)

| Политика | Что делает |
| --- | --- |
| `oracle` | отправляет эталон с первым допустимым набором доказательств на шаге 1 (получает truth от harness) |
| `reconcile` | читает все таблицы через `list_records`, документы-кандидаты на дубль через `get_document`, применяет правила policy |
| `random_explorer` | 3–25 случайных вызовов инструментов (seed фиксирован), затем 0–3 случайных вывода из увиденных ID |
| `flag_all` | читает счета и платежи и обвиняет всё подряд (до 30 выводов, циклически по типам) |

Прогон на 100 seed, конфиг по умолчанию (со сценариями), `scripts/failure_analysis.py`:

| Политика | средняя награда | TP | FP | FN |
| --- | --- | --- | --- | --- |
| reconcile | 0.956 | 425 | 0 | 0 |
| reconcile_ledger_amounts (суммы копируются из книги, правило D37 не применяется) | 0.811 | 359 | 42 | 66 |
| reconcile_naive (дата = первые 10 символов timestamp) | 0.021 | 331 | 346 | 94 |

(Замер после перехода на τ = 0 и D48; до этого было 412 TP, потому что 13 ошибок молча не вносились.)

- Полный reconcile при **нулевом** допуске даёт 0 FP / 0 FN: эталонные суммы точно выводятся из
  открытых записей и policy — это прямая проверка того, что τ = 0 не делает задачу неразрешимой.
- `reconcile_ledger_amounts` ломается **ровно на сценариях**: `period_cutoff` 21 FP/21 FN и
  `unapplied_payment` 21 FP — случаи сценария A (в книге сумма по неверному курсу); ещё 24 FN
  `unapplied_payment` — случаи сценария B (деньги на дубле не считаются нераспределёнными).
- `reconcile_naive`: `fx_error` 219 FP / 34 FN, `period_cutoff` 107 FP / 40 FN, `unapplied_payment`
  20 FP / 20 FN — платежи несут смещение банка, поэтому дата из текста ≠ дата в поясе компании.
- Потеря награды у полного reconcile (1 − 0.956) — только штраф за ≈ 22 шага чтения.
