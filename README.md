# audit-env — RL-среда для дообучения ИИ-аудитора

Воспроизводимый симулятор бухгалтерии **вымышленной** компании за один отчётный период.
Генератор сначала строит согласованную скрытую историю (книга сходится), затем вносит
контролируемые ошибки с записанным причинным изменением. Агент за ≤ 100 шагов исследует
записи через 5 инструментов и отправляет выводы с доказательствами. Оценщик в **отдельном
процессе** сопоставляет их со скрытым эталоном и выдаёт терминальную награду.

Это среда, а не модель: внутри нет обучения весов, LLM, сети, GPU или платных API.
Время работы — только стандартная библиотека Python 3.11+, pytest нужен лишь для тестов.
Все компании, люди, счета и суммы вымышлены.

## 1. Проверка одной командой

```bash
docker build -t audit-env .
docker run --rm --network none --cpus 2 --memory 4g audit-env make check
```

| | |
| --- | --- |

| Рабочая директория | корень репозитория, в контейнере `/app`; точка подключения жюри — `judge_adapter.py` (раздел 4) |
| Результат | `CHECK PASSED`, ненулевой код при любой ошибке; проверка пройдена 22.11.2026 |

### Локально, без Docker

Нужен только Python 3.11+ и git. Скрипт сам создаёт окружение `.venv`, ставит зависимости
точных версий из `requirements.lock` (интернет нужен один раз) и запускает проверку.

```bash
git clone https://github.com/whxythr/genesis.git && cd genesis
```

Windows (PowerShell):

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\check.ps1
```

Linux / macOS:

```bash
sh scripts/check.sh
```

Или через `make`: `make setup` один раз, затем `make check` (Makefile сам берёт `.venv`, если он есть).

### Если что-то не запускается

| Сообщение | Причина и решение |
| --- | --- |
| `pytest is not installed for …` / `No module named pytest` | проверку запустили системным Python, а зависимости стоят в `.venv`. Запускайте `scripts/check.ps1` / `scripts/check.sh` или `.venv` явно: `.\.venv\Scripts\python -m audit_env check` (Windows), `.venv/bin/python -m audit_env check` (Linux/macOS) |
| `No module named audit_env` | не задан путь к коду: `$env:PYTHONPATH="src"` (PowerShell) или `export PYTHONPATH=src` (bash). Скрипты проверки задают его сами |
| `Python 3.11+ not found` | установите Python 3.11 или новее с python.org и повторите |
| «выполнение сценариев отключено» | запускайте именно так: `powershell -ExecutionPolicy Bypass -File .\scripts\check.ps1` |
| `pip install failed` | первый запуск ставит pytest из интернета; дальше всё работает без сети |

### Что делает `make check`

Завершается ненулевым кодом при любой ошибке. Около минуты на обычном ноутбуке.

| Стадия | Что проверяется |
| --- | --- |
| `pytest` | 293 теста: контракт, изоляция, генератор, matcher, атаки на награду, детерминизм, инвариантность, сценарии и **дословные проверки жюри** через адаптер (C01–C20, тесты награды 1–20, M01–M12, матрица D01–D20, пары P01–P20) |
| `validate train / dev` | 10 + 10 эпизодов: инварианты до инъекции, совпадение с эталоном после, достаточность доказательств, **байт-в-байт** совпадение с повторной генерацией из seed |
| `verify train / dev` | независимая проверка **только по файлам**: книги до инъекции восстанавливаются из provenance и сходятся, после видны ровно заявленные расхождения, доказательства достижимы инструментами, форматы раздела 03 |
| `baselines` | 4 базовые политики: train в открытом режиме, dev в закрытом; запись траекторий и таблица P / R / F1 / return / шаги / время |
| `invariance` | 60 парных проверок: эпизод против копии с перемешанными строками и новыми ID |

Ожидаемый конец вывода — `CHECK PASSED`.

## 4. Подключение жюри: `judge_adapter.py`

Тонкий адаптер в корне репозитория. Он переводит формат жюри во внутренний формат среды,
не выбирает действия за политику и не меняет задачу. Импорт — `import judge_adapter` из
корня репозитория (адаптер сам добавляет `src/` в `sys.path`).

```python
import judge_adapter as ja

ja.generate_episode(seed, {"team_config": {...}}, "/jury/ep1")
env = ja.make_env()
obs, info = env.reset(None, {"mode": "closed", "episode_dir": "/jury/ep1", "team_config": {}})
obs, reward, terminated, truncated, info = env.step(
    {"name": "list_records", "args": {"table": "ledger", "cursor": None, "limit": 50}})
ja.score_episode("/jury/ep1", findings, inspection_steps)
```

### Точки входа

| Функция | Поведение |
| --- | --- |
| `generate_episode(seed, config, output_dir)` | генератор команды; `config` — `{"team_config": {...}}` или сами ключи конфига. Пишет в `output_dir` открытые файлы и закрытые `truth.json`, `provenance.json`. Возвращает `None` |
| `make_env()` | объект с методами `reset` и `step` |
| `reset(seed, config)` | `mode: "closed"` — закрытый режим, `"train"` — открытый. С `episode_dir` загружает **именно этот** эпизод, без генерации и без смены ID; повторный `reset` начинает его заново. Без `episode_dir` в train генерирует эпизод по `seed` и `team_config` |
| `step(action)` | действие `{"name": "<действие>", "args": {...}}` |
| `score_episode(episode_dir, findings, inspection_steps)` | закрытый вызов оценщика на стороне жюри, не действие политики |

### Наблюдения

- Первое: `{"task": str, "manifest": object, "policy": object, "remaining_steps": 100}`.
  Описание инструментов — в тексте `task`.
- Следующие: `{"result": value | null, "error": null | {"code": str, "message": str}, "remaining_steps": int}`.
- `info` — всегда `{}` в обоих режимах: TP/FP/FN раскрыли бы число ошибок в эталоне.
- Награда по ходу эпизода — `0.0`. В train терминальная награда приходит в `reward` на шаге
  submit. В closed `reward` равен числовому `0.0` на каждом шаге, включая завершение.

### Действия

| Действие | Аргументы | Результат |
| --- | --- | --- |
| `list_records` | `table` ∈ `ledger`, `invoices`, `payments`, `fx`; `cursor` (первый — `null`); `limit` 1…50; необязательный `filter` (точное совпадение по белому списку полей) | `{"records": [...], "next_cursor": str \| null}`. Записи ровно как в открытых файлах (все поля раздела 03, у счетов — с `line_items`), в порядке файла. Курсоры непрозрачны и стабильны: тот же курсор даёт ту же страницу |
| `get_record` | `table`, `id` | объект записи. Ключи: ledger — `row_id`; invoices — `invoice_id` (или `doc_id`); payments — `payment_id` (или `doc_id`); fx — `fx_id` (или `date:source_currency:target_currency`) |
| `get_document` | `doc_id` счёта или платежа | полный документ |
| `calculator` | `expression`: десятичные числа, `+ - * / ( )`, до 200 символов | десятичная строка, округление half-up до 12 знаков: `0.1+0.2` → `"0.3"`. Свой парсер, без `eval`; код, имена и обращения к файлам — ошибка `CALC_ERROR` |
| `submit` | `{"findings": <findings.json>}` | `{"accepted": true}` или ошибка `INVALID_FINDINGS` (неверная структура). Правильность не сообщается |

### Ошибки

Любая ошибка — фиксированный код и короткое фиксированное сообщение, без эха ввода, путей,
seed и закрытых данных. Ошибка **расходует шаг** и не портит доступ к данным.

| Код | Когда |
| --- | --- |
| `UNKNOWN_ACTION` | неизвестное имя действия |
| `BAD_ARGS` | неверные или лишние аргументы, неверный конверт действия |
| `UNKNOWN_TABLE` | таблицы нет |
| `NOT_FOUND` | записи или документа с таким ID нет |
| `BAD_CURSOR` | курсор подделан или от другого запроса |
| `CALC_ERROR` | выражение вне арифметической грамматики |
| `INVALID_FINDINGS` | submit с неверной структурой: эпизод завершён, награда −1 у оценщика |
| `EPISODE_DONE` | действие после завершения эпизода; ничего не меняет |
| `TIMEOUT` | превышен лимит 60 секунд с начала `reset` |

### Завершение

- Максимум 100 действий, включая submit. Submit на 100-м действии принимается.
- `submit` → `terminated = true`. Последующие действия ничего не меняют.
- 100 исследовательских действий без submit или 60 секунд → `truncated = true`, итоговые findings пусты.

### `score_episode`

Для валидного submit возвращает `{"tp", "fp", "fn", "precision", "recall", "f1", "return"}`.
Для неверной структуры — `return = -1`, остальные поля `null`, плюс `invalid_reason`.
`findings = None` означает «submit не было» (лимит шагов или времени) и оценивается как
пустой ответ. Каждый вызов и каждый эпизод среды пишутся в журнал оценщика
`runs/judge_grader_log.jsonl` (путь задаётся переменной `AUDIT_ENV_GRADER_LOG`).

### Каталог эпизода

```
manifest.json  policy.json  ledger.csv  invoices.jsonl  payments.jsonl  fx.csv   ← открытые
truth.json  provenance.json                                                     ← закрытые
```

Закрытые файлы можно также положить в `<каталог>/closed/`. Их читают только процесс
оценщика и `score_episode`; объект среды получает только открытые данные и путь не хранит.
Для оценки достаточно `truth.json`; `provenance.json` нужен для проверки истории генерации.

Схема всех форм адаптера — [schemas/judge_contract.schema.json](schemas/judge_contract.schema.json).

## 5. Четыре типа ошибок

Каждый тип включается и выключается отдельно (`errors.<тип>.enabled` в конфиге). Валюта суммы
эталона — всегда базовая валюта эпизода. Каждая сумма считается по курсу policy на дату
**самого документа**, как если бы остальные ошибки уже были исправлены.

| `type` | Что меняется | Канонические `affected_ids` | `expected_amount_minor` | Минимальный набор доказательств |
| --- | --- | --- | --- | --- |
| `duplicate_invoice` | счёт повторён с новыми ID (тот же контрагент, валюта, сумма и **идентичные** `line_items`) и проведён второй раз; дубль — более поздний | `[invoice_id дубля]` | сумма дубля в базовой валюте | документ оригинала, документ дубля, транзакция дубля |
| `unapplied_payment` | поступление не распределено (`invoice_refs = null`), распределено частично или одна из ссылок убрана; деньги на счёте-дубле тоже считаются нераспределёнными | `[payment_id]` | нераспределённый остаток в базовой валюте | документ платежа, его транзакция (в сценариях — плюс счета и курс) |
| `fx_error` | документ в иностранной валюте сконвертирован по курсу **другой даты** из `fx.csv`: предыдущий или следующий день, курс недельной давности, дата UTC вместо даты в поясе компании | `[invoice_id или payment_id]` | \|проведено − правильно\| в базовой валюте | документ, строка `fx.csv` правильного курса, транзакция |
| `period_cutoff` | документ датирован после конца периода (с учётом часового пояса), а проводка поставлена внутрь периода | `[invoice_id или payment_id]` | сумма документа по курсу его собственной даты | документ, транзакция (в сценарии A — плюс курс) |

Каноничные правила опубликованы в коде генератора и matcher и не выбираются после прогона.

### Два сценария взаимодействующих ошибок

| Сценарий | Что произошло | Ожидаемые issues |
| --- | --- | --- |
| `partial_fx_payment_at_cutoff` | поступление в иностранной валюте после конца периода проведено в последний день периода, по курсу дня проводки, и распределено частично или не распределено | три на одном `payment_id`: `period_cutoff`, `fx_error`, `unapplied_payment` |
| `partially_paid_duplicate` | счёт продублирован, и частичный платёж распределён на дубль вместо оригинала | две: `duplicate_invoice` (дубль) и `unapplied_payment` (платёж) |

Почему суммы именно такие, с разобранными примерами из train — [docs/DESIGN.md, раздел 4](docs/DESIGN.md).

### Чистые компании и отвлекающие случаи

Чистые эпизоды не содержат ошибок, эталон пуст. Корректные «подозрительные» случаи есть в
каждой компании: разбитые платежи (один счёт — несколько платежей), один платёж на несколько
счетов, возвраты, законно повторяющиеся суммы (подписки), операции поздно вечером, которые по
поясу компании ещё в периоде, корректные конвертации в другую валюту.

### Настройки под каждый закрытый сценарий жюри

[configs/judge_matrix.json](configs/judge_matrix.json) содержит готовый `team_config` для
каждого сценария D01–D20: чистые компании с обычной сверкой, разбитым платежом, возвратом,
подписками и валютной/периодной границей; каждый тип по отдельности, включая пропущенное и
частичное распределение (`errors.unapplied_payment.variants`) и разные варианты неверной даты
курса (`errors.fx_error.variants`); оба сценария взаимодействия. Если запрошенную ошибку нельзя
разместить, компания детерминированно пересобирается; генератор никогда не выдаёт тихо меньше
ошибок, чем задано.

## 6. Данные эпизода

Эпизод — одна компания и один отчётный период: 200–2000 проводок, 20–200 документов,
0–12 ошибок.

| Файл | Поля |
| --- | --- |
| `manifest.json` | `schema_version`, `episode_id`, `base_currency`, `period_start`, `period_end`, `timezone`, `record_counts`, `document_count`, `rounding_rules`, `currency_exponents` |
| `ledger.csv` | `row_id`, `txn_id`, `timestamp`, `account`, `debit_minor`, `credit_minor`, `currency`, `entity_id`, `invoice_id`, `payment_id` |
| `invoices.jsonl` | `doc_id`, `invoice_id`, `entity_id`, `entity_name`, `issued_at`, `due_at`, `currency`, `total_minor`, `line_items` |
| `payments.jsonl` | `doc_id`, `payment_id`, `entity_id`, `kind` (`receipt` / `refund`), `timestamp`, `currency`, `amount_minor`, `invoice_refs` |
| `fx.csv` | `fx_id`, `date`, `source_currency`, `target_currency`, `rate` |
| `policy.json` | границы периода с поясом, правило выбора даты курса и направление пары, округление, счета книги и правила проводок, правила дубля и нераспределённого остатка |

Дополнительные поля по сравнению с кейсом (`txn_id`, `fx_id`, `kind`, `entity_id` у платежей,
`entity_name`) документированы и не раскрывают эталон.

| Формат | Правило |
| --- | --- |
| Время | ISO-8601 со смещением; период `[start, end)`, сравнение моментов времени, календарные даты — в поясе компании |
| Деньги | целые минимальные единицы; разрядность: JPY 0, USD / EUR / KZT / GBP 2, KWD 3 |
| Курсы | десятичные строки, расчёт через `Decimal`, `ROUND_HALF_UP`; курс = единиц целевой валюты за 1 единицу исходной |
| Пропущенные связи | явный `null` (в CSV — пустое поле), никогда не угаданная связь |
| Валюты | разные валюты не сравниваются без конвертации; книга ведётся в базовой валюте |

Закрытые файлы: `truth.json` — `issue_id`, `type`, `affected_ids`, `expected_amount_minor`,
`currency`, `acceptable_evidence_sets` ([схема](schemas/truth.schema.json));
`provenance.json` — seed, версия, конфиг и `config_id`, план генерации, каждое изменение
«было → стало» с причиной, дифф книги до и после инъекции ([схема](schemas/provenance.schema.json)).
По provenance книги до инъекции восстанавливаются и проверяются командой
`python -m audit_env verify <каталог>`.

## 7. Findings, сопоставление и награда

### Формат ответа

```json
{"episode_id": "EP-...", "findings": [
  {"type": "fx_error", "affected_ids": ["PAY-..."], "claimed_amount_minor": 108,
   "currency": "USD", "evidence_ids": ["D-...", "FX-...", "T-..."],
   "explanation": "курс не той даты"}]}
```

### Структура (нарушение → награда −1 и запись в журнале оценщика)

- не больше 30 выводов;
- не больше 10 `evidence_ids` в выводе, считается **до** удаления повторов;
- `explanation` не длиннее 1000 символов Unicode;
- все обязательные поля на месте, JSON-типы верны, лишних ключей нет; `claimed_amount_minor`
  — целое JSON-число (не `"10000"`, не `true`, не `1.5`);
- `episode_id` совпадает с эпизодом.

Структурно верный, но неправильный вывод (неизвестный тип, чужие ID, валюта, сумма,
несуществующее доказательство) — просто FP, не авария эпизода.

### Когда вывод — TP

| Поле | Правило |
| --- | --- |
| `type` | точное совпадение строки |
| `affected_ids` | множество точных строк (регистр и пробелы значимы) совпадает с каноническим набором |
| `currency` | точное совпадение строки, без смены регистра и конвертации |
| `claimed_amount_minor` | \|claimed − expected\| ≤ τ, **τ = 0** для всех четырёх типов |
| `evidence_ids` | все ID существуют в открытых записях, и набор полностью покрывает хотя бы один допустимый набор эталона |

Доказательство покрывается буквально. Одно удобство: канонический ID эталона (`doc_id`,
`txn_id`, `fx_id`) покрывается и другим открытым ID того же объекта (`invoice_id` /
`payment_id`; любой `row_id` транзакции; ключ курса `date:source:target`). Набор из двух
строк книги одной строкой не закрывается. `explanation` в оценке не участвует.

### Сопоставление

Максимальное паросочетание: слева каждый вывод (повторы — отдельные вершины), справа каждая
ошибка эталона. TP — размер паросочетания, FP = выводы − TP, FN = ошибки − TP. Повторный
вывод — FP. При нескольких максимальных паросочетаниях выбирается лексикографически
наименьшая последовательность пар `(issue_id, индекс вывода)`; на TP/FP/FN и награду это
не влияет.

### Метрики и награда

```
P = TP / (TP + FP)    R = TP / (TP + FN)    F1 = 2TP / (2TP + FP + FN)
нулевой знаменатель → 0;  пустой эталон и пустой ответ → F1 = 1;  пустой эталон, выводы есть → F1 = 0
reward = clip(2·F1 − 1 − 0.002·inspection_steps, −1, 1)          возврат эпизода = reward
inspection_steps = все вызовы step до submit, включая ошибочные; сам submit не входит
```

Значения не округляются. Код с нормализацией, допусками и выбором при неоднозначности:
[src/audit_env/grader/](src/audit_env/grader/) (`normalize.py`, `matcher.py`, `metrics.py`, `reward.py`).

Тесты атакующих ответов: полный верный ответ лучше молчания на ошибочных книгах; молчание
лучше ложных обвинений на чистых; дубли не дают выгоды; «пометить всё» даёт плохую награду
(20 выводов при одной ошибке → −871/1050); экономия шагов лишь немного различает равные
ответы; угаданные ID, неподтверждённые и несуществующие доказательства, чужая валюта,
повторный submit, неверный ввод и тайм-аут — `tests/test_judge_matcher.py`, `tests/test_reward.py`.

## 8. Изоляция и режимы

- Эталон загружается только в **отдельном процессе оценщика** (`grader/service.py`, JSON по
  stdin/stdout). Объект среды получает открытые данные; ссылок на truth, provenance и пути к
  ним в нём нет.
- Через инструменты нельзя получить shell, SQL, файловую систему или сеть.
- Эталон не утекает через наблюдения, пути, тексты ошибок, `info`, порядок строк (внесённые
  записи упорядочены вместе с остальными по ID, а не собраны в конце файла: на train + dev
  медиана относительной позиции добавленных строк книги — 0.62) и ID (непрозрачные, без
  «dup», «err» и последовательных подсказок).
- `train`: терминальная награда возвращается политике. `closed` (внутреннее имя `eval`):
  награда `0.0` на каждом шаге, `info = {}`, результаты остаются у оценщика до конца прогона.
- `reset` полностью изолирует эпизод; `reset` посреди эпизода оценивает его как брошенный
  (пустой ответ).

Проверяется: `tests/test_isolation.py`, `test_c19_*`, `test_c20_no_leak_anywhere`,
`test_adapter_env_object_holds_no_truth`.

## 9. Воспроизводимость и версии

- Вся случайность — через `random.Random`, созданный из `(seed, назначение, config_id)`;
  нет глобального `random`, `hash()` от строк, времени и `uuid` в данных.
- Повтор с теми же seed, конфигом, версией и действиями воспроизводит записи, переходы и
  награды; файлы эпизодов совпадают байт в байт (`make validate`, `tests/test_determinism.py`).
- Конфиги версионированы: `configs/default.json`, `configs/train/v1.json`,
  `configs/dev/v1.json` (имя + список seed). У каждого эпизода есть `config_id` = имя
  конфига + хеш полностью разрешённого конфига; он и версия кода пишутся в provenance и в
  каждую строку траекторий.
- Инвариантность: `python -m audit_env transform --split dev --seed 7` пишет копию набора с
  перемешанными строками и новыми ID; `make invariance` сравнивает награды oracle, reconcile
  и flag_all на 20 парах.

## 10. Базовые политики, диагностика и демо

| Политика | Что делает |
| --- | --- |
| `random_explorer` | 3–25 случайных действий с фиксированным seed, затем 0–3 случайных вывода из увиденных ID |
| `reconcile` | простой алгоритм сверки только через инструменты: ищет дубли, нераспределённые остатки, сверяет курсы по policy и границы периода |
| `flag_all` | атака «пометить всё»: обвиняет всё подряд, до 30 выводов |
| `oracle` | только для оценщика: получает эталон от харнесса (не от среды) и отправляет верные выводы обычным submit — проверяет, что максимум награды достижим |

Диагностика из `make check` (средние по 10 эпизодам):

| Политика | train: P / R / F1 | train: return | dev (closed): P / R / F1 | dev: return | шаги | время на эпизод |
| --- | --- | --- | --- | --- | --- | --- |
| oracle | 0.60 / 0.60 / 1.00 | 1.000 | 0.70 / 0.70 / 1.00 | 1.000 | 1 | 0.02–0.03 с |
| reconcile | 0.60 / 0.60 / 1.00 | 0.957 | 0.70 / 0.70 / 1.00 | 0.957 | 22.3 | 0.02–0.03 с |
| random_explorer | 0.00 / 0.00 / 0.20 | −0.607 | 0.00 / 0.00 / 0.20 | −0.605 | 16.9 / 14.6 | 0.02–0.03 с |
| flag_all | 0.00 / 0.00 / 0.00 | −1.000 | 0.00 / 0.00 / 0.00 | −1.000 | 3.3 / 3.1 | 0.02–0.03 с |

Средние P и R ниже 1 даже у oracle: на чистых эпизодах (4 в train, 3 в dev) TP + FP = 0,
и по правилу кейса P = R = 0, хотя F1 = 1. Высокая награда oracle сама по себе не означает
сложности — это проверка достижимости максимума.

Демо — скриптовая политика проходит эпизод шаг за шагом и печатает итоговые выводы с вердиктом
оценщика, P / R / F1 и награду:

```bash
make demo        # или: python -m audit_env demo
```

## 11. Траектории

`trajectories/train/trajectories.jsonl` (открытый режим) и
`trajectories/dev_eval/trajectories.jsonl` (закрытый): одна строка на шаг.

| Поле | Значение |
| --- | --- |

## 12. Разбор сбоев и ограничения

Измеренный разбор сбоев — [docs/DESIGN.md, раздел 7](docs/DESIGN.md). Кратко:

- на 100 seed reconcile при допуске τ = 0 даёт 425 TP / 0 FP / 0 FN; если брать дату как
  первые 10 символов времени (без учёта пояса) — 346 FP; если копировать суммы из книги —
  42 FP / 66 FN, ровно на сценариях взаимодействия;
- найдено и исправлено при сверке с определениями жюри, с цифрами «до» и «после»: генератор
  тихо выдавал меньше ошибок (10 из 150 seed → 0), округление награды (ошибка 3.3·10⁻⁷ при
  допуске 10⁻⁹ → 0), нестрогое сравнение строк, допуск 0.1 %, урезанные записи счетов,
  одна строка закрывала набор из двух, `info` раскрывал TP/FP/FN.

Ограничения, у каждого — замер или сценарий проверки, — [docs/DESIGN.md, раздел 6](docs/DESIGN.md).
Главные:

- генератор публичный: зная конфиг, seed можно подобрать перебором по `episode_id`
  (≈ 75 тыс. seed/с), поэтому закрытые seed нужно брать из ≥ 2³²;
- `fx_error` моделирует неверную дату курса, а не произвольное значение курса;
- награда среды не доказывает пригодность модели для реального аудита; веса не обучались,
  и об улучшении обучения мы не заявляем.

## 13. Подключение своей модели

Для официальной проверки модель не нужна. Для экспериментов подходит любой агент, который по
наблюдению выбирает действие: RL-агент в любом фреймворке (контракт в стиле Gymnasium, всё в
JSON) или LLM с tool calling (5 действий = 5 инструментов). Агенту на LLM через API нужен
интернет — это допустимо для экспериментов, но не для официальной проверки.

```python
import judge_adapter as ja

env = ja.make_env()
obs, _ = env.reset(7, {"mode": "train", "team_config": {}})
done = False
while not done:
    action = my_model.choose(obs)   # {"name": ..., "args": {...}}
    obs, reward, terminated, truncated, _ = env.step(action)
    done = terminated or truncated
env.close()
```

Обучайте на train, сравнивайте на dev: заявлять об улучшении модели без контролируемого
сравнения на отложенных данных нельзя.
